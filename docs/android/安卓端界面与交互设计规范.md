> **状态**：待评审。评审通过后再改代码。

## 0. 先说三个真实缺陷（不是审美问题，是 bug）

用户反馈里有两项**必须当 bug 修**，它们与"好不好看"无关：

| # | 现象 | 根因 | 性质 |
|---|---|---|---|
| B1 | 返回按钮**和手机状态栏重叠，点不到** | `MainActivity` 调了 `enableEdgeToEdge()`，但**全文没有任何 inset 处理**。内容从屏幕物理顶端开始绘制，于是画到了状态栏底下 | 🔴 功能性缺陷 |
| B2 | **右滑返回直接退出软件** | 路由是我手写的 `var route by remember { ... }`，**从未注册系统返回处理**。系统认为"无处可退" → 退出 App | 🔴 功能性缺陷 |

另外两项是设计问题：

| # | 现象 | 根因 |
|---|---|---|
| B3 | "完全就是把文字摆上去" | 没有设计令牌、没有层级（卡片/容器）、没有间距系统、没有按压反馈；`EmptyState` 是纯文字居中 |
| B4 | 不像安卓软件，没有底部标签栏 | 只有单层首页，无 `NavigationBar`；导航形态不是安卓习惯的"底部标签 + 页内层级" |

> **本规范的自我要求**：B1/B2 必须用**可验证的方式**证明已修（见 §7 验收清单），
> 不能只凭"我改了"。

## 1. 设计语言（对齐仓库现有视觉，不另创一套）

### 1.1 关键决定：沿用仓库已有的暖色系，废弃我之前自创的冷蓝

我此前给安卓端用的是 `#4C8DFF` 冷蓝 + `#0E1116` 冷黑，**这与 ShortCut 既有视觉完全不同**——
难怪看起来"不像这个软件"。仓库里的真实设计语言是**暖褐底 + 米白字 + 砖红强调**。

**证据**（对 `server/sync/web/**` 全部颜色做频次统计，2026-10-13）：

| 出现次数 | 色值 | 用途 |
|---|---|---|
| 18 | `#f6efe5` | 主文字（暖白） |
| 15 | `#aaa198` | 次级文字（暖灰） |
| 10 | `#26231f` | 页面底色 |
| 10 | `#24221f` | 页面底色（另一处） |
| 9 | `#9f493a` | **强调色（砖红）** |
| 8 | `#33302c` | 卡片面 |
| 8 | `#3a3631` | 次级面 / 按钮 |
| 7 | `#948b82` | 弱化文字 |
| 6 | `#eee4da` | 按钮文字 |
| 6 | `#c8beb3` | 说明文字 |
| 6 | `#e5a19a` | 错误文字（暖红） |
| 5 | `#8ac49f` | 成功（暖绿） |
| 4 | `#2c2925` | 顶部栏 / 输入条 |
| 4 | `#0c1015` | 输入框内底（深） |
| 3 | `#63b582` | 在线绿点 |
| 3 | `#8f877e` | 离线灰点 |

桌面端 `src/index.css` 另有一套强调色 `#e85d04`（橙），`resources/icon.svg` 也是橙底闪电。
**安卓端取"暖褐 + 砖红"这套**——因为它是**移动端已在用的**（`/mobile/`、`/taskwall/`、`/transfer/`、`/bind/` 四个页面一致），
而手机用户看到的就是它。桌面端的橙属于桌面语境。

### 1.2 设计令牌（全部落在 Material 3 的语义色位上）

不另造一套 `ScColor` 常量直接到处引用——那样会绕开 M3 的深浅色机制。
正确做法是**把仓库色值映射进 `ColorScheme` 的语义槽位**：

| M3 槽位 | 深色值 | 取色理由 |
|---|---|---|
| `background` | `#24221f` | 页面底 |
| `onBackground` | `#f6efe5` | 主文字 |
| `surface` | `#2c2925` | 顶栏/面板 |
| `surfaceContainer` | `#33302c` | 卡片 |
| `surfaceContainerHigh` | `#3a3631` | 次级按钮/输入框 |
| `surfaceVariant` | `#36322d` | 分组底 |
| `onSurfaceVariant` | `#aaa198` | 次级文字 |
| `outline` | `rgba(255,255,255,.12)` | 描边（web 里统一是白色低透明） |
| `primary` | `#9f493a` | 砖红主操作 |
| `onPrimary` | `#ffffff` | — |
| `primaryContainer` | `#3a2b29` | 危险按钮底（web 的 `.danger`） |
| `error` | `#e5a19a` | 暖红 |
| `tertiary` | `#8ac49f` | 成功（暖绿） |

浅色主题：沿用桌面 `[data-theme="light"]` 的思路（`#f7f7f8` 底 + 深字 + `#d35400` 强调），
但**本轮先只做深色打磨到位**，浅色保持可用即可（见 §6 范围）。

### 1.3 圆角、描边、阴影（三者是"廉价感"的主要来源）

我在对照 web 之后发现，web 之所以看起来"成套"，靠的是**一致的圆角 + 极细描边 + 克制的阴影**：

| 令牌 | 值 | 依据 |
|---|---|---|
| 卡片圆角 | `10–12dp` | web `.nav-card` / `.card` 用 12px、10px |
| 按钮圆角 | `8–10dp` | web `.btn` / `.primary` 用 8–10px |
| 小控件圆角 | `8dp` | web `.icon-btn` 8px |
| 胶囊圆角 | `999dp` | web `.pill` / `.chip` |
| 卡片描边 | `1dp` `rgba(255,255,255,0.09)` | web 卡片统一 `rgba(255,255,255,.09)` |
| 卡片阴影 | 几乎不用；只在浮层用 | web 卡片**不投阴影**，靠描边+面色区分 |
| 浮层阴影 | `0 18px 50px rgba(0,0,0,.3)` | web `.card`（浮层态）、`.sheet` |

> ⚠️ **纠错**：我之前给卡片加了 Material 默认 elevation，深色下会显得"灰扑扑发脏"。
> 深色主题里**描边比阴影更干净**，这也是 web 的做法。

### 1.4 间距系统（8dp 栅格）

web 的 padding 高度一致（`.shell` 18–26px、`.card` 14–24px、gap 8–12px）。
安卓端固定成 8dp 栅格：`4 / 8 / 12 / 16 / 20 / 24 / 32`。
**禁止** 出现 `13.dp`、`17.dp` 这类随手值（我现在代码里就有 `14.dp`、`18.dp` 混用）。

### 1.5 字体（M3 字阶，不用裸 `fontSize`）

| 用途 | M3 字阶 | 说明 |
|---|---|---|
| 页面标题 | `titleLarge` (22sp) | 对齐 web `h1` 18–22px |
| 卡片/列表主标题 | `titleMedium` (16sp) | web `.nav-card b` 16px |
| 正文 | `bodyMedium` (14sp) | web 正文 14px |
| 次级说明 | `bodySmall` (12sp) | web `.sub`/`.card p` 12px |
| 标签/角标 | `labelSmall` (11sp) | web `.pill` 11px |

> ⚠️ **纠错**：我现在代码里直接写 `fontSize = 30.sp`（首页图标）。
> 图标尺寸应走独立的 `IconSize` 令牌，不是字阶。

### 1.6 触摸目标（B1 的直接教训）

**最小 48dp × 48dp**（Android 无障碍硬要求）。
我此前用 `TextButton { Text("← 返回") }`——`TextButton` 有内边距但视觉上仍是"一行小字"，
用户明确反馈"那么小直接和状态栏重叠都点不到"。改为标准 **`TopAppBar` + `IconButton`**（48dp 触摸目标）。

## 2. 导航架构（B4 + B2 的解决方案）

### 2.1 结论：迁移到 Navigation Compose

我现在的做法是手写：

```kotlin
private sealed interface Route { ... }
var route by remember { mutableStateOf<Route>(Route.Splash) }
```

它带来三个问题，**其中 B2 是硬伤**：
1. **没有返回栈**（B2）——系统返回直接退出 App；
2. 状态不保留：切到设置再回来，首页滚动位置与板块内子页全丢；
3. 无法参与 predictive back（API 33+ 的"拖动预览"动画）。

改用 `androidx.navigation:navigation-compose`（已在依赖里，2.8.2）：

```kotlin
NavHost(navController, startDestination = "home") {
    composable("home")     { HomeScreen(...) }
    composable("settings") { SettingsScreen(...) }
    composable("module/{id}", arguments = listOf(navArgument("id") { type = NavType.StringType })) {
        ModuleHostScreen(moduleId = it.arguments!!.getString("id")!!, ...)
    }
    composable("bind")     { BindScreen(...) }
    composable("module/{id}/{sub}") { ... }   // 板块内子页
}
```

**收益**：返回栈天然正确（B2 修好）、`saveState/restoreState` 保留状态、
`NavHost` 与 `BackHandler` 协同、将来做深链（通知点击跳转）也现成。

> **代价**：`ModuleNavigator` 的 `to()/back()` 要从"改一个 `mutableStateOf`"
> 改为操作 `NavController`。这是框架层的改动，**板块代码不受影响**——
> 因为它们只调 `navigator.to("子页")`，这正是当初把导航收敛成接口的价值。

### 2.2 底部标签栏（用户明确要求）

```
┌──────────────────────────────┐
│  TopAppBar（标题 / 状态）      │
├──────────────────────────────┤
│                              │
│        内容区（NavHost）       │
│                              │
├──────────────────────────────┤
│   🏠 首页        ⚙️ 设置       │   ← NavigationBar
└──────────────────────────────┘
```

- 用 M3 `NavigationBar` + `NavigationBarItem`，放在 `Scaffold(bottomBar = ...)`。
- **只在顶层两个页面显示**；进入板块或详情页时隐藏（`currentBackStackEntryAsState` 判断路由）。
- 2 个标签（首页/设置）。M3 建议 3–5 个，但**2 个是合法且常见的**（如"主页+更多"）。
  将来本机功能变多，可扩到 3–4 个，无需改架构。
- 标签文字**始终显示**（`alwaysShowLabel = true`）——工具类 App 图标辨识度不够，纯图标会让人猜。

### 2.3 层级返回规则（B2 的完整语义）

| 当前位置 | 系统返回 / 右滑应去哪 |
|---|---|
| 首页（标签根） | **退出 App**（正确行为） |
| 设置（标签根） | 回首页 |
| 某板块主页 | 回首页，**标签栏恢复显示** |
| 板块内子页（如"新建任务"） | **回该板块主页**，不退到首页（我此前会一路退到首页） |

实现：板块子页在 `ModuleHostScreen` 里注册 `BackHandler`；
板块内 `ModuleNavigator.back()` 与系统返回走**同一个**出口，保证行为一致。

## 3. 页面骨架（统一"样式包裹"）

用户说"你多加一些样式包裹"——指的是**每个页面都该有的骨架层次**。
统一成三层，任何页面都不得裸奔：

```
Scaffold
├── topBar     : TopAppBar（标题、可选返回箭头、可选状态点）
├── bottomBar  : NavigationBar（仅顶层页）
└── content    : 内容区
      ├── 外层 padding（16dp）+ 状态栏/导航栏 inset
      └── 内容容器
            ├── 卡片（surfaceContainer + 1dp 描边 + 12dp 圆角）
            ├── 分组标题（labelLarge + onSurfaceVariant）
            └── 列表项
```

### 3.1 三态视图重做（现在是"纯文字居中"，最廉价的部分）

| 状态 | 现状 | 改为 |
|---|---|---|
| Loading | 转圈 | 转圈 + 说明文字（"正在读取…"），保持骨架间距 |
| Empty | 一行灰字 | **图标（64dp，30% 不透明）+ 标题 + 说明 + 可选操作按钮**，圆角虚线描边容器 |
| Error | 红字 + 按钮 | **图标 + 标题 + 具体原因 + 重试按钮**；`retryable=false` 时不显示重试 |

参照 web `.clip-empty`：`border: 1px dashed` + 居中 + padding 24px。
这个"虚线圆角空态"是 web 里已有的手法，安卓端照搬即可，立刻不像"裸文字"。

### 3.2 列表项标准形态（对齐 web `.nav-card`）

web 的卡片是「**图标方块 + 标题/副标题 + 右箭头**」的横向行，不是星罗棋布的网格方块。
用户要"像导航页"，但对**列表型内容**（任务、笔记、设备）应使用这种行式卡片。

```
┌────────────────────────────────────────┐
│ ┌────┐  任务标题                  ›    │
│ │ 🗂️ │  副标题 / 元信息                │
│ └────┘                                 │
└────────────────────────────────────────┘
   46dp方块   flex:1                     20sp
```

- 图标容器：`46dp` 圆角 `11dp`，底色 `surfaceContainerHigh`（web `.nav-ico` 是 46px/11px）
- 行高 ≥ `64dp`，全行可点
- 按压反馈：`Modifier.clickable` 默认 ripple + `scale(0.98)`（web `.nav-card:active`）

### 3.3 首页：网格还是列表？

用户说"每个板块做一个单独的图标点进去跳转""整体像导航页"。
参照 web `/mobile/` 用的是**纵向卡片列表**；但用户明确提到"图标"。

**折中方案**：首页用**网格图标**（快速启动，符合"导航页"直觉），
但**每个图标格子做成有包裹感的卡片**（图标容器 + 名称），而不是裸图标裸文字。
分区标题（"本机功能"/"连接电脑"）用 `labelLarge` + 左右对齐的分隔线，让它看起来是"分组"。

> 这一点我想请你确认：**首页要网格还是列表**？见 §8-Q1。

## 4. 与 web 的对照改进清单

| web 已有、安卓端缺失的 | 安卓端要做的 |
|---|---|
| 24px 网格纹理背景 | 可选：Compose `drawBehind` 画极淡网格（web 是靠 `linear-gradient` 网格）。**建议先不做**，手机屏幕小，易显脏（见 §8-Q2） |

## 6. 范围与不做的事

- **本轮只打磨深色**；浅色保持"能用、不丑"即可（web 也只有深色为主）。
  若你要浅色也精细，我另开一批。
- **不做**：自定义启动图、动效大片、3D、复杂图形（都是"廉价感"的常见反效果）。
- **不做**：把 emoji 换成自定义矢量图标集（web 也全程用 emoji，属既有风格，换掉反而不一致）。
  但**首页图标格子**里的 emoji 会加容器包裹，不再是裸字符。

## 8. 待你确认

### Q1 首页形态：网格 还是 列表？

- **A 网格图标**（我现在做的，加卡片包裹）：快速启动，像"应用抽屉"，适合板块多
- **B 行式卡片列表**（web `/mobile/` 的做法）：信息量大，副标题能写清功能，更像"导航页"
- **C 网格图标 + 每区最多 8 个，多的进"更多"**：折中

### Q2 要不要那层 24px 网格纹理背景？

web 四个页面都有（很淡的白线网格），是它"有质感"的来源之一。但手机屏幕小、像素密度高，
