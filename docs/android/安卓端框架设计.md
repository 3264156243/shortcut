## 0. 为什么重做这一层

P0 那版框架**结构上只能装"联动板块"**（依赖桌面绑定），装不下用户要的安卓自有功能。两处硬编码就是证据：

| 位置 | 现有代码 | 后果 |
|---|---|---|
| `ModuleRegistry.resolve()` | `serverById[module.id] ?: return@mapNotNull null` | 服务端没声明的板块**永不显示** → 纯本机功能加不进来 |
| `ModuleHostScreen` | `!identity.isBound -> EmptyState("请先连接电脑")` | 未绑定就一律拦住 → 本机功能也被挡 |

**修正后的定位**：绑定码是**「联动能力」的钥匙**，不是整个 App 的钥匙。
两种板块（本机 / 联动）在框架里**同等地位、各自热插拔**。

## 1. 设计原则（全部来自用户要求）

| # | 原则 | 落到设计上的体现 |
|---|---|---|
| 1 | **以绑定码为轴，但不被它绑死** | `bindId` 是全局唯一身份，只有联动的板块才消费它；本机板块完全不感知 |
| 2 | **热插拔** | 加板块 = 加一个文件 + 注册表一行；框架自动接上入口、图标、权限、"未绑定"处理 |
| 3 | **不一次定死** | 首页布局、设置项、板块元数据都设计成**可叠加**的：先给最小实现，但接口留好（§3.3 / §4.3） |
| 4 | **整体像导航页** | 首页 = 板块图标网格；每个板块一个图标，点进各自页面；不做底部 Tab（板块数量会一直涨） |

## 2. 板块模型（框架的核心抽象）

### 2.1 两类归属域

这是本次要加的关键字段。**板块自己声明归属域，框架据此决定要不要绑定、要不要跟服务端对账。**

| | **本机板块 LOCAL** | **联动板块 LINKED** |
|---|---|---|
| 依赖绑定 | ❌ 不需要 | ✅ 需要 |
| 是否参与服务端 `module.list` 对账 | ❌ 不参与（服务端不认识它） | ✅ 参与（服务端可远程开关/改元数据） |
| 断网/未绑定可用 | ✅ 完全可用 | ⚠️ 未绑定置灰，绑定后解锁 |
| 元数据来源 | 本地声明 | 服务端优先、本地兜底 |
| 元数据字段冲突 | 不受服务端影响 | 受 `enabled` / `minAppVersion` 影响 |
| 典型板块 | 笔记、扫码、计算器、记账、剪贴板历史… | 任务墙、文件快传、电脑控制 |

> **为什么只分两类**：这是用户明确要的两类。第三类（"本机优先、绑定后增强"，如笔记本地存+云同步）表达力更强，
> 但会让框架和**每个**板块都多处理一套冲突/同步逻辑。等真有需求再说——按 §1.3「不一次定死」，这是加枚举值即可的低成本扩展。

### 2.2 能力（capability）

板块声明它用哪类通道，框架据此提供**共享底座**（§5），避免每个板块各写一套。

| capability | 用途 | 共享底座 | 现状 |
|---|---|---|---|
| `QUEUE` | 队列型（任务下发/拉取） | `core/queue/` | 已实测（P1 任务墙） |
| `BLOB` | 文件分片上传下载 | `core/blob/` | 待做 |
| `REALTIME` | 实时长连接（电脑控制） | `core/realtime/` | 待做 |
| `RPC` | 一次性调用 | `core/rpc/` | 待做 |
| `NONE` | 本机板块不用通道 | — | 立即支持 |

### 2.3 板块声明（加板块就是写这个文件）

```kotlin
class NotesModule : ShortcutModule {
    override val spec = ModuleSpec(
        id = "notes",
        label = "笔记",
        icon = "📝",
        desc = "随手记，存在本机",
        domain = ModuleDomain.LOCAL,      // ← 本机板块：不需要绑定
        capability = Capability.NONE,
        order = 10,                        // 首页默认排序（可被用户布局覆盖，见 §3.3）
    )

    @Composable override fun Screen(nav: ModuleNavigator) { /* 页面 */ }
}

class TaskwallModule : ShortcutModule {
    override val spec = ModuleSpec(
        id = "taskwall",
        label = "任务墙",
        icon = "🗂️",
        desc = "把任务从手机钉到桌面任务墙",
        domain = ModuleDomain.LINKED,     // ← 联动板块：需要绑定 + 服务端对账
        capability = Capability.QUEUE,
        minAppVersion = "2.4.5",
        order = 100,
    )

    @Composable override fun Screen(nav: ModuleNavigator) { /* 页面 */ }
}
```

### 2.4 框架代劳的事（板块一行都不用写）

1. 首页入口卡片：图标、标题、描述（`module.list` 优先、本地兜底）
2. **未绑定时的置灰与"去绑定"提示**（LINKED 专属；LOCAL 不受影响）
3. `enabled=false` / 无 `entry` 的隐藏、`minAppVersion` 版本门禁
4. 首页排序与分组（先按 `order` + 域分组，后续可被用户布局覆盖）
5. 请求自动带 `bindId` + `mobileToken`
6. 身份失效 → 清本地身份 + 跳绑定页（幂等，只触发一次）
7. 服务端文案 → 提示语的映射
8. loading / 空态 / 错误 / 重试
9. 板块内子页导航（`ModuleNavigator.to()`）
10. 按需申请权限、按需起停前台服务
11. 设置页分片挂载

## 3. 首页（导航页）

### 3.1 形态

```
┌─────────────────────────────────────┐
│  ShortCut                    设置 ⚙ │
│  已连接 · 我的手机  /  未连接电脑      │
├─────────────────────────────────────┤
│  本机功能                            │
│  ┌────┐  ┌────┐  ┌────┐             │
│  │ 📝 │  │ 📷 │  │ 🧮 │   ← 图标网格  │
│  │笔记│  │扫码│  │计算│             │
│  └────┘  └────┘  └────┘             │
├─────────────────────────────────────┤
│  连接电脑                            │
│  ┌────┐  ┌────┐  ┌────┐             │
│  │ 🗂️ │  │ 📤 │  │ 🖥️ │             │
│  │任务│  │快传│  │控制│             │
│  └────┘  └────┘  └────┘             │
└─────────────────────────────────────┘
```

- **分区**：`本机功能` / `连接电脑`。两类可用条件不同，分开用户一眼就懂。
- **未绑定**：`连接电脑` 区的图标**置灰可点**，点击弹「先连接电脑 → 去连接」，而不是隐藏
  （用户要求：让人知道产品有哪些能力）。
- **为什么不用底部 Tab**：板块会持续增加，Tab 数量是固定槽位，加了就得重排；网格天然可扩展。

### 3.2 数据来源

**注册表（本地声明）+ 服务端清单（仅 LINKED）+ 布局覆盖层（用户偏好）**，三者合成最终展示列表。

### 3.3 预留扩展点（用户明确提到"后续支持自定义板块位置、分组、移动、标签、搜索"）

这一轮**不实现**这些功能，但把接口留好，避免以后重构首页：

```kotlin
/** 用户对首页的个性化。先只实现默认值，字段留全。 */
data class HomeLayout(
    /** moduleId → 顺序（缺省用 ModuleSpec.order） */
    val orderOverrides: Map<String, Int> = emptyMap(),
    /** moduleId → 自定义分组名（缺省用域分组） */
    val groupOverrides: Map<String, String> = emptyMap(),
    /** 被用户隐藏的 moduleId */
    val hidden: Set<String> = emptySet(),
    /** moduleId → 标签（用于将来的标签筛选） */
    val tags: Map<String, List<String>> = emptyMap(),
)

interface HomeLayoutStore {
    suspend fun load(): HomeLayout
    suspend fun save(layout: HomeLayout)
}
```

- 现在用 `InMemoryHomeLayoutStore`（即默认布局）
- 将来做"长按拖动排序"时，换成 DataStore 实现 + 在首页调用 `save()`，**首页渲染代码不用改**
- 搜索：在合成后的列表上做过滤，不改变数据来源

## 4. 设置页（分片式）

### 4.1 结构

设置页由**若干分片（Section）**组成；分片可以来自框架核心，也可以由板块贡献。

```
设置
├── 外观          ← 核心分片：字号、主题
├── 连接与设备     ← 核心分片：绑定信息、设备名、解绑
├── 存储          ← 核心分片：缓存管理、占用统计
├── 消息通知       ← 核心分片（预留，配合将来的推送）
├── 激活管理       ← ⚠️ 待确认（见 §9-Q1）
├── ── 板块设置 ── ← 以下由各板块贡献
├── 任务墙设置     ← TaskwallModule.SettingsSection()
└── 关于          ← 核心分片：版本、协议版本、开源许可
```

### 4.2 板块贡献分片

```kotlin
interface ShortcutModule {
    /** 板块自己的设置分片；默认空实现 → 设置页不会为它生成任何条目 */
    @Composable fun SettingsSection(): Unit = Unit
}
```

### 4.3 预留扩展点

加一个设置分片 = 加一个文件（框架分片）或让板块实现 `SettingsSection()`。
用户提到"很多东西不想一次定死"，所以**设置项按分片拆分、不写成一个巨型 SettingsScreen**。

## 5. 共享能力底座（用户要求："两层都定好"）

### 5.1 为什么必须共享

契约 §7.6 硬约束：**同一 `bindId` 最多 3 条连接**（1 桌面 + 2 手机）。
如果任务墙、控制各建一条 WS，再加一个板块就直接 `too many connections`。
所以实时通道**必须**是全局单例，而不是每板块一条。

### 5.2 底座职责

```
core/
├── queue/      队列型：push / pull / ack / board.list
├── blob/       分片型：fileInit → chunk(0-based 连续) → fileComplete → download
├── realtime/   实时型：一条 WS，ticket/auth-ok/ping-pong/api-res 分发
│               └── 生命周期由框架持有，板块只订阅消息
└── rpc/        一次性调用
```

**分工**：底座负责"连接、重连、心跳、限流退避、身份注入、错误归一"；
板块只负责"业务字段与 UI"。这样加第二个 `REALTIME` 板块时**不需要**再写一条连接。

## 7. 扩展点速查表

| 以后要加什么 | 要改哪里 | 要改几处 |
|---|---|---|
| 一个**本机**功能板块 | 新建 `feature/local/xxx/XxxModule.kt` + `Modules.kt` 一行 | **1 个文件 + 1 行** |
| 一个**联动**功能板块 | 新建 `feature/linked/xxx/` + `Modules.kt` 一行（服务端 `modules.json` 由桌面侧加，客户端**零改动**即显示） | **1 个文件 + 1 行** |
| 板块内的子页面 | 板块自己 `navigator.to("子页")` + 读 `LocalModuleSubRoute` | 板块内 |
| 板块的设置项 | 板块实现 `SettingsSection()` | 板块内 |
| 一个设置分片 | 新建分片文件 + 注册 | 1 个文件 + 1 行 |
| 首页自定义排序/分组/标签/搜索 | 实现 `HomeLayoutStore`（DataStore 版）+ 首页交互 | **首页渲染代码不改** |
| 推送接入 | 实现 `core/push/PushGateway` + 设置页"消息通知"分片 | 框架层 |
| 新协议能力 | `core/<capability>/` 加一个引擎 | 框架层 |

**验收方式**：`feature/local/demo` 与 `feature/linked/taskwall` 作为两条路的样例。
两者都能被注册表识别、在首页正确分区、未绑定时表现正确（LOCAL 可用 / LINKED 置灰）——
则框架成立。

- **C**：只是**跳转到桌面端那个激活后台网页**的快捷入口
