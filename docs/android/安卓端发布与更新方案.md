# 安卓端 · 发布与更新方案（热更新可行性评估）

> **状态**：✅ **方案 B 已落地**（2026-10-16）。用户决策：B + 正式 keystore + 启动自动检查。
> **归属**：安卓侧（`android/**`、`docs/android/**`）。
> 建立：2026-10-14 · 触发："先做一个框架级别的工作，实现热更新，不然每次都要我重新下"

---

## 0. 结论（已实现）

**Android 原生应用不存在"完全无感热更新"**，这是平台限制：

| 想更新的东西 | 能否不重装就生效 | 依据 |
|---|---|---|
| **前端页面/交互代码**（若用 Web 承载） | ✅ 可以 | 就是网页，服务端改完刷新即用 |
| Kotlin 字节码（界面、业务逻辑） | ❌ 需要装 APK | Android 14+ 每次安装**必须用户手动确认** |

**已实现方案 B**：App 内检查更新 → 下载 → 引导安装。
用户从"找文件传到手机"变成"点两下"；**数据与绑定都保留**。

> 若将来"改界面"频繁到无法忍受，再考虑方案 A（见 §2.A）——
> 但那要重写 7000+ 行 Compose 界面，成本已在 §2.A 实测列出。

## 1. 平台硬约束（先认清边界）

### 1.1 Android 14 / 15 的安装限制

| 版本 | 变化 | 对本项目的影响 |
|---|---|---|
| **Android 14** | 安装来源 App 不能再"一次授权永久有效"，**每次安装都要用户再确认** | 无法做到"点一下自动装好"，**必须用户点确认** |
| Android 14 | 目标 SDK < 23 的 APK 无法安装 | 我们 targetSdk 35，无影响 |
| **Android 15** | **静默安装全面封杀**：非用户主动点击触发的安装会被拦 | 彻底断掉"后台自动更新"的幻想 |
| Android 15 | Play Protect 实时行为扫描 | 自签名的自用包可能被提示"未知来源"，需用户放行 |

> 结论：**任何"APK 自动更新"方案，都至少需要用户点 2–3 次**（下载 → 允许安装 → 确认）。
> 我们能做的是把"重新找链接下载"变成"App 内一键提示更新"。

### 1.2 关于 Google Play 的"动态代码加载"禁令

Google Play 政策禁止 App **自动修改、替换自身**（动态代码加载）。
本项目**不上架 Google Play**（自有服务器分发），所以这条政策不约束我们 ——
但这也意味着我们**不能借用 Play 的更新通道**，得自己搭。

## 2. 三条可选路径

### 方案 A：WebView 壳 + 服务端下发界面（**真正免重装**）

**核心思路**：APK 只保留"原生能力"（扫描、相机、文件、前台服务、WebSocket），
**界面全部由服务端下发的网页承载**。

```
┌────────────────────────────────────┐
│  APK 壳（很少变）                    │
│  · 原生扫码 / 相机 / 文件选择          │
│  · 前台服务 / WS 长连接               │
│  · 一个 WebView                      │
└──────────────┬─────────────────────┘
               │ 加载
               ▼
   https://shortcut.326415.xyz/app/   ← 界面在这里，改完即生效
```

| 维度 | 评价 |
|---|---|
| 功能更新是否要重装 | ✅ **不用**，改服务端刷新即生效 |
| 原生能力（扫码等） | 通过 JS 桥接调用，一次性写好 |
| 现成资产 | ✅ **`server/sync/web/**` 已经是这样**（5 个页面，靠 `sdk.php` 透传） |
| 首次安装 | 仍需装一次 APK |
| 代价 | ① 界面需重写成 Web ② 手感不如原生 ③ 依赖网络 |

#### ⚠️ 必须如实说明的成本（实测数据）

| | 行数 | 说明 |
|---|---|---|
| 现有 **web 端**全部页面 | **2843 行** | 已经是服务端下发的，质量可参考 |
| 安卓端 **Kotlin 总量** | 10191 行 | — |
| 其中**界面层**（`feature/` + `ui/`） | **7371 行（72%）** | 方案 A 会让这部分**大部分作废** |

**也就是说**：方案 A 不是"复用已有工作"，而是**把 7000 多行 Compose 界面换成约 3000 行的 Web 界面**——
工作量不小，且这两天刚调好的原生手感（触控板手势、差量输入、粘滞修饰键）要重做一遍。

**它真正的价值**在于：**此后再改界面就永远不用重装了**。是否值得，取决于你后续改界面的频率。

### 方案 B：APK 内"检查更新 + 下载 + 引导安装"（**实现最省，但不是热更新**）

App 启动时查服务端版本，发现新版就提示并引导安装。

```
启动 → GET /app/android/latest.json
     → 版本更高？显示"有新版本 v0.2.0，本次更新：…"
     → 用户点"下载" → 下载 APK（带进度与 sha256 校验）
     → 调系统安装器 → 用户点"允许安装"→ 完成
     → 配置与登录态保留（同签名覆盖安装）
```

| 维度 | 评价 |
|---|---|
| 用户操作 | 点 2–3 次（下载 / 允许安装 / 确认） |
| 是否要重装 | **要**（覆盖安装，但**数据不丢**、**不用重新绑定**） |
| 实现成本 | **低**——可**直接复用桌面端已有的更新基建** |
| 与现有资产 | ✅ 复用 `latest.yml` 结构、`publish-update.ps1` 脚本、服务器 `/updates/` 目录 |
| 原生界面 | ✅ **完全保留**，不浪费已有工作 |

> **可复用的现成资产**（已核实）：
> - 服务器 `https://shortcut.326415.xyz/updates/latest.yml` 已有版本+sha512+更新说明的结构
> - `scripts/publish-update.ps1` 的发布流程（构建 → 校验产物 → scp 上传）
> - `release-notes/` 的版本说明机制
>
> 安卓端只要**平行建一套 `updates/android/`**，复用同样的字段设计即可。

### 方案 C：Tinker / Sophix 式字节码热修复（**不推荐**）

| 维度 | 评价 |
|---|---|
| 原理 | 下载差分补丁，运行时替换 dex/资源 |
| 对本项目的代价 | ① 需预埋框架并**改 Application/类加载** ② 与加固/混淆冲突 ③ 每个基线版本都要维护补丁包 ④ 出问题极难排查 ⑤ **Android 15 起静默安装被封，但补丁是代码注入，不触发安装** —— 技术上仍可行 |
| 适配成本 | 高（要重构现有代码结构，且**每次改基线都要重打补丁**） |
| 适用场景 | 大型 App、发版周期长、线上崩溃要紧急修 |

> **判断**：本项目是**自用/小范围分发**，且我在**快速迭代功能**（今天一天就改了 6 轮）。
> 热修复适合"稳定版本上的紧急小修"，而我们恰恰相反 ——
> 引入它的复杂度会**远大于**它省下的那几次点击。
> **明确不建议。**

## 3. 我的建议：**先做 B，签名立刻做**

### 3.1 立刻做（方案 B）

理由：**成本最低、保留已有 7000+ 行界面、可复用桌面端基建**，
把"你自己找链接下载"变成"App 内一键更新"。

**先纠正一个可能的预期**：方案 B 下**你仍然需要点几下安装**（Android 14+ 硬限制），
但差别很大：

| | 现在 | 方案 B 之后 |
|---|---|---|
| 你做什么 | 等我说"新 APK 好了" → 找文件 → 传到手机 → 安装 | App 内弹"有新版本" → 点下载 → 点安装 |
| 数据 | — | **不用重新绑定**（覆盖安装保留） |
| 更新说明 | 我在聊天里说 | App 内显示 |

### 3.2 关于方案 A 的判断（实测数据后）

**我倾向"暂不做，但留好路"**，理由是成本对比很悬殊：

| | 现在 | 换成方案 A |
|---|---|---|
| 界面代码 | 7371 行 Kotlin（已调好手感） | ≈3000 行 Web（全部重写） |
| 触控板手势、差量输入、粘滞修饰键 | 已调好并通过 194 个单测 | 需在 Web 上重做一遍 |
| 此后的界面改动 | 每次要重装（方案 B） | **永不重装** |

**判据**：如果"改界面"的频率**长期**维持在像这两天这么高，方案 A 迟早划算；
如果只是**开发期**频繁，等稳定下来就少了，那方案 B 足够。

> **我的建议**：先用方案 B 顶住（今天就能有），
> 等你觉得"又是重装"烦到一定程度，再上方案 A —— 那时界面也稳定了，重写一次更值。

### 3.3 无论选哪个，**签名必须现在做**

这是**不可逆**的：keystore 丢了 = 再也无法给已安装用户推送更新（签名不一致会被系统拒绝）。
规范 §5 已把它列为红线。**这一条与选哪个方案无关，必须做。**

具体设计：

```
GET https://shortcut.326415.xyz/updates/android/latest.json
{
  "versionCode": 2,
  "versionName": "0.2.0",
  "apkUrl": "https://…/updates/android/ShortCut-0.2.0.apk",
  "sha256": "…",
  "size": 44236800,
  "releaseNotes": "## 0.2.0\n- 修输入同步\n- 键盘单键/组合分支修正",
  "releaseDate": "2026-10-15T…",
  "minSupportedVersionCode": 1
}
```

App 侧行为：
1. 启动时（及设置页手动点）拉这个 JSON
2. `versionCode` 更大 → 弹窗显示版本号 + 更新说明
3. 用户点"下载" → 下载到应用私有目录，**校验 sha256**（校验失败不提示安装）
4. 调系统安装器（`ACTION_VIEW` + `FileProvider`）→ 用户确认安装
5. **覆盖安装保留数据**（同签名 → `deviceKey`/绑定态都在，不用重新绑定）

> 关键点：**签名必须固定**。keystore 丢了 = 再也无法给已安装用户更新（规范 §5 已列此红线）。
> 这件事现在就得做：**生成正式 keystore 并离线备份**，之后所有版本都用它签名。

### 3.2 何时该升级到方案 A

如果出现以下情况，说明"每次要重装"的痛点已经值得付 WebView 的代价：
- 界面/交互需要**每天多次**调整（就像这两天）
- 你希望手机上看到的总是最新界面，**完全不想管版本号**

**折中路线**：不推翻现有 Compose，而是**新增**一个"实验性 WebView 承载"的板块，
先把变动最频繁的部分（如电脑控制面板）搬过去验证手感，再决定是否扩大。

### 7.2 更新链路（已实现）

```
启动 → 静默拉 /updates/android/latest.json
     → versionCode 更大？弹窗显示版本号 + 更新说明
     → 用户点「下载更新」→ 下载（带进度）
     → ★ sha256 校验通过 → 显示「立即安装」
     → 调系统安装器 → 用户在系统框里点「安装」
```

| 组件 | 位置 |
|---|---|
| 清单模型（含 `versionCode` 判据） | `core/update/UpdateManifest.kt` |
| 拉清单 + 下载 + **sha256 校验** | `core/update/UpdateClient.kt` |
| FileProvider + 系统安装器 | `core/update/ApkInstaller.kt` |
| 状态机（检查/下载/安装） | `core/update/UpdateViewModel.kt` |
| 对话框 UI | `core/update/UpdateDialog.kt` |
| 手动入口 | 设置 → 关于 → 「检查更新」 |

**两个刻意的设计决定**：

1. **判据用 `versionCode`（整数），不用 `versionName` 字符串**
   —— 照抄桌面端会出错：`"0.10.0"` 按字典序**小于** `"0.9.0"`，会永远提示不了更新。
2. **sha256 校验失败必须删文件且不提示安装**
   —— 否则用户会装到一个损坏或被篡改的包，表现为"更新装不上"甚至更糟。

### 8.4 途中发现并修掉的两个隐患

**隐患 1：线上 `latest.json` 的 `Content-Type` 不带 `charset=utf-8`**

响应头只有 `application/json`。缺 charset 时部分 HTTP 客户端会按**平台默认编码**
（Windows 上是 GBK）解码 → 中文全变乱码。

我们依赖 OkHttp 的 `body.string()`（缺省 UTF-8）—— 这是**假设**，不是保证。
所以加了 `LiveUpdateManifestTest` 打**真实线上**验证：中文能正确解出
（含「应用内更新」）、无 GBK 误解码痕迹、APK 大小与清单一致。
实测 **2/2 通过、0 跳过**。

**隐患 2：`-Dsc.*` 参数没透传到测试进程**

`LiveUpdateManifestTest` 加完后一直显示"跳过 2 个"——因为 Gradle 的 `-D`
只作用于守护进程，**不进 fork 出来的测试 JVM**，`System.getProperty` 拿到 null；
而 `build.gradle.kts` 里只透传了固定两个 key。

已改成**前缀匹配 `sc.*`**，以后加新线上测试不用再改这里。

> 这个坑很隐蔽：测试"成功地被跳过"看起来像通过，实际**什么都没验**。
> 与之前那条"用测试给 bug 盖章"是同一类问题 —— **绿色不等于验过**。
> 所以线上测试的结果文件要额外看 `skipped` 计数，不能只看 BUILD SUCCESSFUL。
