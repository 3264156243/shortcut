## 1. 待安卓侧回复

> 每条都给了**我的建议答案**。同意的话只回"同意 + 简短理由"即可，别让它变成负担。

### Q1 `applicationId` 最终定什么？

- **我需要**：一句话确认，例如 `com.wanan.shortcut`。
- **为什么**：OPPO 推送平台是按**应用**（AppKey）+ 包名 + 签名指纹绑定的。开通推送后再改包名/签名 = 推送失效。
  另外我在写服务端配置与文档时要引用它，越早定越好。
- **建议**：`com.wanan.shortcut`（与桌面端 app id 一致）。若你想加后缀（`…​.mobile`）也行，**定了就别再改**。

> **安卓侧回复**：

### Q2 推送目标用 `regId` 逐个推，还是用**别名（alias）**一次覆盖？

- **建议：别名**。把 alias 设成 `bindId`（或 `bindId:deviceId`），服务端**推一次自动覆盖该绑定下所有已订阅设备**。
- **为什么**：OPPO 单推支持 `target_type=2`（registration_id）与 `5`（别名）。走 regId 的话，服务端要维护
  "一个绑定 → N 台手机各自的最新 regId"，还要处理换机/重装的陈旧 regId；走别名则设备侧自己订阅/退订，
  服务端只认 `bindId`——与现有绑定体系天然对齐。
- **需要你确认**：① 用别名还是 regId；② 若用别名，**别名格式**定成 `bindId` 还是 `bindId:deviceId`
  （后者便于将来只推某一台）。

> **安卓侧回复**：

### Q3 `regId` 什么时候上报？

- **建议：绑定成功后立刻上报 + 每次冷启动再上报一次**（regId 会随重装/清数据变化，且 OPush 可能刷新）。
- **为什么**：只报一次的话，重装后服务端拿的是废 regId，推送静默丢失；每次上报的目标是让服务端**覆盖**旧值。
- **需要你确认**：上报时机；以及"用户拒绝通知权限"时是否仍上报（建议仍上报，避免权限恢复后又得等下次启动）。

> **安卓侧回复**：

### Q4 点击通知后打开哪里、带什么参数？

- **我需要**：一种"点击行为契约"，因为通知体（`notification` 里的 click 相关字段）是**服务端组装**的。
- **建议**：统一带 `bindId` + 业务键（`taskId` / `fileId`），落地页：任务 → 任务墙、文件 → 文件页、其余 → 首页。
- **需要你确认**：① 打开哪个 Activity/页面；② 接受的参数名（例：`{"page":"taskwall","taskId":"rmt_…"}`）；
  ③ 是"App 内自绘通知"还是"用系统通知栏消息"（后者不需要 App 进程活着——**推荐**，也是 ROADMAP 里选的）。

> **安卓侧回复**：

### Q5 App 在前台时还要不要弹通知？

- **建议：前台不弹**（避免与已有的中继 WS 实时重复打扰）。判断方式由你定（前台服务/Activity 生命周期）。
- **需要你确认**：是否有"App 在前台"的标识能反馈给服务端，还是纯客户端去重即可（**推荐后者**，服务端无状态更简单）。

> **安卓侧回复**：

### Q6 服务端那半（`push.register` + 设备行字段 + OPPO 网关）谁写？

- **背景**：按《协同开发规范》§3，`server/**` 归桌面侧，且**部署只有桌面侧能做**。
- **建议**：**我实现 + 部署**（我会在契约里先加 `push.register` 与设备行 `push_reg_id/push_provider/push_updated_at`，
  再写 PHP 网关，AppKey/MasterSecret 放服务器 `data/` 目录不入库）。你只需按契约调用。
- **也接受**：如果你更想自己写服务端 → 提 PR 只动 `server/**`，我 review + 部署（**密钥与部署仍归我**）。
- **需要你确认**：走哪种。

> **安卓侧回复**：

### Q7 你的分支名 & 首个可拉取版本大概什么时候？

- **我要做什么**：你说过"拉你分支看一眼就知道"——我确实会**定期拉取你的分支做协议对齐检查**
