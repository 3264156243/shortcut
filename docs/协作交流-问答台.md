### Q2 推送目标用 `regId` 逐个推，还是用**别名（alias）**一次覆盖？

- **建议：别名**。把 alias 设成 `bindId`（或 `bindId:deviceId`），服务端**推一次自动覆盖该绑定下所有已订阅设备**。
- **为什么**：OPPO 单推支持 `target_type=2`（registration_id）与 `5`（别名）。走 regId 的话，服务端要维护
  "一个绑定 → N 台手机各自的最新 regId"，还要处理换机/重装的陈旧 regId；走别名则设备侧自己订阅/退订，
  服务端只认 `bindId`——与现有绑定体系天然对齐。
- **需要你确认**：① 用别名还是 regId；② 若用别名，**别名格式**定成 `bindId` 还是 `bindId:deviceId`
  （后者便于将来只推某一台）。

### A2. `minAppVersion` 的版本命名空间冲突（**已导致线上可见故障，建议改契约**）

- **场景**：安卓端把 `module.list` 下发的 `modules[].minAppVersion`（线上值 `2.4.5`）
  当作"客户端版本下限"拿来做门禁，结果为：**任务墙 / 文件共享 / 电脑控制全部被永久锁死**，
  界面显示"需升级"、点不进去。用户在真机上直接遇到了（2026-10-14 反馈）。
- **根因**：该字段装的是**桌面端**的版本号（`2.4.5` 来自你仓库的 `package.json` 体系），
  而安卓端是 `0.1.0`。**两者不是同一个命名空间**，`0.1.0 < 2.4.5` 恒成立。
  契约 §4.1 写的是"服务端不做任何强制，是否门禁完全由客户端决定（**安卓端建议自行比较**）"，
  但按字段的实际内容，安卓端**根本无法正确比较** —— 这是个契约缺口。
- **我已做的临时处理**（只动安卓侧，未碰服务端）：
  - 停止使用 `minAppVersion` 做门禁；
  - 新增可选字段读取 `minAndroidVersion`（服务端当前不下发 → 不门禁）；
  - 加回归测试锁住"绝不用桌面版本号卡安卓客户端"。
- **需要你确认（三选一）**：
  1. **（推荐）**在 `modules.json` / `module.list` 增加 `minAndroidVersion` 字段
     （值用安卓端版本号，如 `"0.1.0"`），安卓端已支持读取，你加了就生效；
  2. 或在契约里**明确写明** `minAppVersion` 仅适用于桌面端/移动 Web，
     **安卓端不得用于门禁**（我按此执行）；
  3. 或改为按端下发（如 `minVersions: { desktop, android, web }`）。
- **期望时间**：不阻塞我当前工作（已用临时方案绕开），但建议尽早澄清 ——
  这个坑的失败表现是"功能看起来在、但永远点不进去"，很容易被误判成别的故障。

### A3. `lan_urls()` 可能返回手机连不上的虚拟网卡地址（**建议增强，安卓侧已容错但治标不治本**）

- **场景**：用户真机反馈"**局域网都无法连接**"（2026-10-14）。
- **我查到的根因**（读 `src-tauri/src/control.rs:789`）：
  ```rust
  fn lan_urls(port: u16) -> Vec<String> {
      if let Ok(addrs) = std::net::UdpSocket::bind("0.0.0.0:0") {
          let _ = addrs.connect("8.8.8.8:80");   // ← 靠"默认出口网卡"猜地址
          if let Ok(local) = addrs.local_addr() { ... out.push(...) }
      }
      // 双网卡补充：…… 交给 /api/status 由前端展示主地址   ← 注释承认未实现
      out
  }
  ```
  两个问题：
  1. **装了 VMware / VirtualBox / Docker 的电脑上，`UdpSocket.connect("8.8.8.8:80")`
     很容易选中虚拟网卡**（如 `192.168.56.1`、`172.17.0.1`），
     这个地址手机**根本连不上**，但桌面端会当成"主地址"下发。
  2. 源码注释里的"**双网卡补充**"**并未实现**，所以 `urls` 实际只有一个候选，
     选错就没有备选（`/api/lan-entry` 里的 `urls` 数组形同只有一个元素）。
- **影响面**：web 端拿到这个地址后是 `location.href = d.url + '/?token=…'`
  —— **浏览器直接跳转，失败就是白屏**，用户和我都无从判断是"地址错"还是"网络不通"。
  移动端体验上表现为"点了没反应/打不开"。
- **安卓侧已做的容错**（只动安卓侧，未碰桌面端）：
  - 不只用 `url`，**把 `urls` 数组也当作候选**，用无需鉴权的 `/api/config`
    逐个探测（带超时），**只连真正可达的那个**；
  - `LanChannel` 不再"一创建就宣称可用"：网络类失败即降级，
    界面会立刻从"已连接"变成"未连接"（避免"显示已连但每条指令都失败"）；
  - 全部候选不可达时，给出**可诊断的原因**（不同 Wi-Fi / AP 隔离 / 防火墙 / 虚拟网卡），
    并提示可回退云端。
  - 有 10 个单测覆盖（含"从多个候选中挑出真正可达的那个"）。
- **需要你确认（建议至少做第 1 条）**：
  1. **（推荐）`lan_urls()` 枚举本机所有私有 IPv4**（排除回环、虚拟网卡与 Docker 网段），
     全部放进 `urls`，让客户端自己挑可达的 —— **这也是你们注释里原本的计划**；
     识别虚拟网卡可参考网卡名（`vEthernet`/`VMware`/`VirtualBox`/`vboxnet`/`docker`）或
     用 `GetAdaptersAddresses` 读 `IfType`；
  2. 或在 `/api/lan-entry` 里**带上网卡名**，让客户端能在 UI 上显示"正在试哪个网卡"，
     便于用户自己排除；
  3. 或至少在 `/api/status` 的局域网状态卡里同时显示**全部候选地址**，
     用户可手填另一个（安卓端已支持"备用手动填地址"）。
- **期望时间**：不阻塞我当前工作（安卓侧已能挑出可达地址），
  但**如果桌面端只给一个虚拟网卡地址，安卓端就只能报错回退云端**，
  局域网低延迟的优势用不上。建议在第 1 条上投入一点。
