# 移动互联架构现状与目标（2026-10-07）

> 背景：项目要"走稳移动互联板块"，后续新增板块（剪贴板、语音、笔记…）应当是**在原架构上加一块功能**，
> 类似热插拔、不影响既有架构。本文先回答一个问题：**现在的实现到底是不是按这个理念做的？**
> 结论一句话：**身份层（绑定码/bindId/token）确实做成了全平台共用的地基；但"通用通道 + 板块热插拔"这一层没有落地 —— 现在是"一个身份 + 三套各写各的协议"。**

---

## 一、原本的设计理念（来自两份计划文档）

`docs/移动端联动开发计划.md` §3/§5.2、`docs/文件快传与通用移动联动开发计划.md` §2/§5.1 写得很明确：

1. **一个绑定身份**：一台桌面 = 一个 `bindId`（+6 位绑定码 + 二维码），所有联动板块共用，不再为每个功能建另一套绑定。
2. **一条通用云同步通道**：服务端 `sync/api.php` 以 `action + board` 分发；客户端 `syncEngine.registerConsumer('taskwall', fn)`。
3. **板块只做两件事**：服务端加一个 `board` 分支 + 客户端注册消费回调 + 一个 Web 入口。

也就是说，理念是"**平台 + 插件**"。验收这个理念是否落地，应该看：新增一个板块**需要改几处、动多少存量代码**。

## 二、现状实测（逐条对理念核验）

### ✅ 身份层：真的按理念做了

- 绑定产物统一：`bindId` + 6 位绑定码 + 二维码直链 + `mobileToken`（一对一、重新绑定即轮换旧令牌失效）。
  服务端实现见 `server/sync/config.php:224-246`（`issue_mobile_token` / `validate_mobile_token` 用 `hash_equals`）。
- 移动端三页共用同一份绑定存储：`shortcut-mobile-binding-v1`（`web/mobile/index.html:66`、`web/taskwall/index.html:122`、`web/transfer/index.html:92`、`web/control/...`、`web/bind/index.html`）。
- 桌面端三块功能都从同一个 `bindId` 出发：任务墙 `sync.rs:69`、文件快传 `transfer.rs`、云控制 `cloud.rs`（读 `config.sync`）。
→ **这一层是干净的，可以作为地基继续用。**

### ❌ 通道层：没有统一，每个模块自带协议

服务端 `api.php` 的 action 命名空间实测分布：

| 命名空间 | 数量 | 性质 |
|---|---|---|
| `bind.*` | 5 | 身份（共用） |
| `mobile.*` | 1 | 身份（共用） |
| **通用队列** `push`/`pull`/`ack`/`board.*` | 4 | 只有任务墙在用 |
| `transfer.*` | 9 | 文件快传自带一整套 |
| `control.*` | 1 | 控制板块自带（+ 独立 WebSocket 中继） |

三种完全不同的传输模型并存：
1. **队列型**（任务墙）：`push → pull → ack`，服务端按 bindId 落队列；
2. **请求/响应 + 分片型**（文件快传）：`transfer.fileInit/fileComplete` 走 `api.php`，分片走**另一个入口** `file.php`（multipart、2 MB 分片、`dl_` 一次性令牌）；
3. **实时中转型**（电脑控制）：`control.ticket` 换 10 分钟票据 → 走独立的 `wss://…/relay-ws`。

→ 理念里的"一条通用通道"实际只有任务墙享受到了。新板块目前无法复用通道，只能再写一套。

### ❌ 没有"模块注册表 / 能力清单"

在 `server/sync/api.php`、`config.php` 全文检索 `module|registry|capab|feature`：**0 命中**。
服务端不知道"这台桌面/这个手机启用了哪些模块、每个模块有什么能力、需要什么权限"。
客户端模块列表是**编译期硬编码**：`src/moduleRegistry.ts:32`（桌面）、`server/sync/web/mobile/index.html:44-60`（移动端三张卡片写死在 HTML 里）。

→ 新增板块 = 往 `api.php` 的大 switch 里塞 case + 移动端加一页 + 手改 `mobile/index.html` 卡片。这不是热插拔，是"继续往一个文件里堆"。

### ❌ 鉴权强度每个模块不一致（这正是审计里 S1/S2/S3 的根因）

| 模块 | 桌面上报身份的方式 | 强度 |
|---|---|---|
| 文件快传（`api.php:55-63`） | `side` **由客户端自报**，只有 `mobile` 才校验令牌 | 桌面侧等于无凭证 |
| 分片上传/下载（`file.php:24-28`） | 同上 | 同上；下载还走 GET 查询串 |
| 电脑控制（`api.php:179-183`） | 桌面角色用**绑定码**当凭证 | 而绑定码可被 `bind.info` 无凭证索回 |
| 任务墙（`api.php:350-353`） | 同上模式 | 同上 |

→ 同一个绑定身份，在不同模块上的校验方式、强度、限流都不一样，且没有统一的"鉴权中间件"。平台化最该统一的一层反而最散。

### ❌ 桌面端没有统一引擎

理念里的 `syncEngine.registerConsumer('taskwall', …)` 在 Tauri 版**没有实现**：`src-tauri/src/sync.rs` 里是硬编码的 `pull_taskwall()`（`sync.rs:168`），没有注册表、没有消费回调机制。
绑定身份被各自解析：`sync.rs` 5 处 + `transfer.rs` 4 处（`cloud.rs` 另读 `config.sync`），**没有共享缓存**——`sync.rs:73` 每次 `get_bind_info()` 都会真发一次 `bind.info` 网络请求（所以一次文件上传 = 3 次 `bind.info`）。

### ❌ 移动端没有共享 SDK、没有协议版本

五个页面各自声明同一个 storageKey（5 处），各自实现绑定读取、请求封装、错误提示、轮询——**没有 `sdk.js` 之类的共享层**；也检索不到 `protocolVersion`/`apiVersion` 之类的协议版本号。
后果：将来服务端协议一变，要同时改五个页面，且无法灰度/兼容旧版移动壳（而下一步正要写 Capacitor 安卓壳）。

### ❌ 权限/配额/用量只声明未消费

- 后台已有字段：`fileTransferPolicy{maxFileMb, cloudQuotaMb, shareEnabled, maxShareHours, retentionHours}`（`server/activation/index.php:1182-1202`）。
- 服务端只有 `retentionHours` 被读（`config.php:621`），且取**所有用户组的最大值**而非按组；单文件上限、云空间配额、分享开关、最长分享时长**全都没校验**。
- 文档 §6.3 的用量看板字段：仓库内未见实现。

## 三、判断：理念落地了多少

| 理念要素 | 落地情况 |
|---|---|
| 单一绑定身份，全板块复用 | **已落地**（且实现质量不错：令牌轮换 + `hash_equals`） |
| 一条通用云同步通道 | **未落地**（只有任务墙走队列；快传/控制各自造协议） |
| 板块只注册消费者、热插拔 | **未落地**（服务端无模块抽象、桌面无注册表、移动端卡片硬编码） |
| 权限策略可下发可校验 | **半成品**（字段有、消费几乎没有） |
| 新板块"加一块功能"不影响存量 | **不成立**：现在新增一个板块要动 **4 处**（`api.php` 加 case、桌面加一个 `xxx.rs` 并各自解析绑定、移动端加页、`mobile/index.html` 手加卡片），且鉴权写法靠复制粘贴 |

一句话：**"绑定码这个地基"是真的统一了，但地基上面还盖着三间各自打桩的房子。**

## 四、目标架构（走稳的做法）

目标是让"新增板块"变成一个**声明 + 一个消费回调**。分四层：

### 1. 身份层（先加固，收敛到一处）
- `bindId` 保持唯一身份；凭证升级为**服务端签发的 `deskToken` / `mobileToken`**（服务端存 hash，可轮换、可失效）。
- 服务端提供**唯一鉴权入口** `auth(side, token)`（中间件），所有模块接口强制过它；`side` 不再由客户端自报，而由**凭证类型**决定。
- `bind.info` / `bind.resolve` 不再回传绑定码；`control.ticket` 桌面角色改用 `deskToken`。
- 桌面端把身份放进**一处持有 + 内存缓存**（带 TTL），不再每个模块各发一次 `bind.info`。

### 2. 模块契约层（服务端的"插件接口"）
- 服务端新增 `server/sync/modules.json`（模块注册表）+ `module.list` 端点，下发：
  `{ id, label, icon, entry, minAppVersion, capabilities:[queue|blob|realtime|rpc], policy:{enabled,maxFileMb,quotaMb,...} }`，按 bindId → 用户组过滤。
- 模块按能力实现**同一组端点**，服务端只提供四种能力，不新增协议：
  - `queue`：`module.push / pull / ack`（任务墙现有语义直接泛化）
  - `blob`：`blob.init / chunk / complete / status / download`（快传现有语义泛化，`status` 同时解决"缺片查询/断点续传"）
  - `realtime`：`realtime.ticket` + WS（控制板块现有语义泛化）
  - `rpc`：`module.invoke`（一次性动作，如"让桌面打开某文件"）
- 每类能力共用同一套鉴权、限流、配额、错误格式。

### 3. 桌面引擎层（Rust 单一入口）
- 新增 `hub.rs`：持有身份 + 请求封装 + 模块注册表 + 队列消费者（`hub.register("taskwall", fn)`），
  `transfer.rs` / `cloud.rs` 逐步迁到同一身份与请求层，模块只实现"消费/上报"。
- 模块启停统一由 `module.list` 的 `policy.enabled` 决定（替代现在"卸载面板即停"的副作用）。

### 4. 移动端壳层
- `/mobile/` 由 `module.list` **数据驱动渲染**卡片（服务端加减模块不用改 HTML）。
- 抽 `server/sync/web/sdk.js`：绑定、鉴权、请求重试、错误/toast、轮询；五个页面改为引用它。
- 页面/请求带 `protocolVersion`，为后续 Capacitor 壳留兼容余量。

## 五、迁移策略（不破坏线上）

1. **先加固身份层**（P0 全部：S1/S2/S3/S12）——这是所有后续工作的前提，且改动小。
2. **建模块契约**：新增 `module.list` + 泛化 `queue`（任务墙迁移，它本来就符合语义），旧 `push/pull/ack` 保留为别名，老移动页不受影响。
3. **迁移文件快传**到 `blob` 能力（含 `status` 缺片查询 → 顺带实现断点续传），旧 `transfer.*`/`file.php` 保留别名到新端点。
4. **迁移电脑控制**到 `realtime` 能力。
5. **迁移移动端**：抽 `sdk.js` + `/mobile/` 数据驱动，五页逐个换。
6. **补权限与用量**：所有模块调用统一走 `policy` 校验；补用量字段。

## 六、"热插拔"的验收标准（可自证）

新增一个假想板块（例：剪贴板）时，**只允许改三处**：
1. 服务端：`modules.json` 加一条 + 实现该模块的一个能力处理函数（不碰 `api.php` 大 switch 的其它 case）；
2. 桌面端：`hub.register("clipboard", consumer)` 一行 + 该模块自己的业务代码；
3. 移动端：**零改动**（卡片与入口由 `module.list` 渲染）。

只要还能出现"必须改 `mobile/index.html` 才能加卡片"或"必须复制一套鉴权代码"，就说明还没走稳。
