# SC 球「启用穿透」开关失效 —— 根因与修复（2026-10-13）

> 后续补充见文末 **§8 穿透 vs 拖放的两条不变量**（2026-10-14）：
> 穿透只影响"能不能拖走球"，绝不影响"能不能把文件拖到球上"。

## 1. 用户报告

「转换设置里的 sc球启用穿透」要挪到 SC 球板块；并且**开关启停没用：显示状态变了，但实际还是可穿透的**。

## 2. 根因（日志实证，不是推测）

应用日志（`%LOCALAPPDATA%\com.wanan.shortcut\logs\tauri.log`）里，用快捷键 Ctrl+Alt+B 反复切换时：

```
[01:38:00] [island] island 鼠标穿透：请求=false 实际可穿透=true ex=0xC0138
[01:38:02] [island] island 鼠标穿透：请求=true  实际可穿透=true ex=0xC0138
[01:38:08] [island] island 鼠标穿透：请求=false 实际可穿透=true ex=0xC0138
```

`ex=0xC0138` 里含 **WS_EX_TRANSPARENT（0x20）**：Windows 侧始终是"穿透"。而**「请求=false」那一行上面没有打印
`[island] 穿透生效 = …`**——说明 `apply_island_and_ball_passthrough_value()` 被缓存提前 return 了，
**根本没去碰窗口样式**。

两个叠加原因：

| # | 位置 | 问题 |
|---|---|---|
| ① | `windows.rs::effective_island_passthrough()`（旧） | 用户开关只在**展开态**有意义：`if 开关 { true } else { displayState != "expanded" }`。收起/迷你态下，开关 ON 与 OFF **算出来的值都是 true**。 |
| ② | `windows.rs::apply_island_and_ball_passthrough_value()` | `PASSTHROUGH_APPLIED` 缓存"值没变就不下发"。①导致值确实没变 → 连样式都不碰 → 从系统层面看**永远穿透**。 |

要命的是默认值：`island.ballClickThrough` 默认 false（开关关），而岛默认是收起态 → **默认就是"恒穿透"**。

## 3. 为什么不能简单地"关掉就不穿透"

岛窗口是**固定 360×340 的透明窗**（`ISLAND_WIDTH/HEIGHT`），收起态的球只占其中一小块。
一旦整窗接收鼠标，球周围那一大圈透明区就会**吞掉桌面点击**——这正是一开始写成
"非展开态一律穿透"的原因。所以正确修法不是"整窗可交互"，而是：

> **不穿透时，只在"可见内容"上可交互；其余区域继续穿透。**

## 4. 修复

### 4.1 穿透判定（`src-tauri/src/windows.rs`）

`effective_island_passthrough(app)` 改为四级：

1. 拖拽进行中 / 拖放菜单打开 → **不穿透**（否则收不到拖放、点不到菜单）——保持原样
2. **用户开关打开（启用穿透）→ 恒定穿透**（连球一起穿透，交给下层窗口）
3. 展开态 → **不穿透**（整窗可交互，原行为不变）
4. 收起 / 迷你态 → **跟随可见内容**：光标在球的矩形内 → 不穿透；移开 → 穿透

第 4 条是本次修复核心：开关终于对"收起态"也有意义了，同时球周围不挡桌面。

### 4.2 "可见内容矩形"从哪来

新增 `ISLAND_HIT_RECT`（逻辑像素，窗口坐标）+ `set_island_hit_rect()`；
岛前端（`src/island.tsx`）在挂载 / 布局变化时把 `.island-root` 的 `getBoundingClientRect()`
经新 IPC `islandHitRect` 上报（ResizeObserver + 1s 兜底轮询 + rAF 去抖，值不变不重复 IPC）。
未上报时默认取整窗（退化为"整窗可交互"，与改动前展开态一致，安全兜底）。

### 4.3 顺带清理

- 删掉死代码 `apply_passthrough(win)`（它用的是不带光标的旧判定，且**从未被调用**——编译警告一直在报它）。
- 拖放守卫的轮询间隔改为**自适应**：只有在"穿透值会随光标变化"时（开关关 **且** 非展开态）才用 40ms，
  其余 120ms。慢了会出现"快速点一下球没反应"。
- 新增日志：`[island] 可见内容矩形 = (x,y,w×h)`，便于现场核对命中框。

## 5. 设置项搬家

| | 之前 | 现在 |
|---|---|---|
| 位置 | 转换板块 → 齿轮设置 → 「SC 球」小节 | **SC 球板块 → 「鼠标穿透」小节**（`IslandPanel.tsx`） |
| 文案 | 「未穿透（收起态仍按岛的显示状态：收起穿透、展开可交互）」 | 明确写清两种状态的实际行为（见下） |

## 8. 穿透 vs 拖放的两条不变量（2026-10-14）

### 8.1 用户报告

「拖拽文件识别转换只有在 SC 球**不可穿透**状态下可以使用，应该可不可以穿透都支持；
是否穿透只会影响能不能拖拽 SC 球位置。」

### 8.2 两条不变量（这是设计约定，别再搞混）

| 行为 | 受穿透开关影响？ |
|---|---|
| **按住球拖动移动位置** | ✅ **受影响**：穿透开着时不能拖走球（穿透 = 不接收鼠标，连拖动一起关掉） |
| **把文件从资源管理器拖到球上**（识别格式 → 出现转换按钮） | ❌ **不受影响**：无论是否穿透都必须能接到文件 |

实现上分别对应两处：

- 拖动移动位置：`island.css` 里 `-webkit-app-region: drag` 收敛到 `.island-shell.grabbable`，
  由 `island.tsx` 按穿透开关动态加类（穿透时去掉 → OS 层起不了拖窗）。
- 文件拖放：由 Rust 的**拖放守卫**（`spawn_island_drop_guard`）保证——它轮询"左键按住 + 光标在岛附近"
  → 临时把窗口变成可交互（`mark_drag_active`），让 Windows 的 OLE 命中测试不再跳过岛。

### 8.3 根因：守卫轮询太慢，抢不过系统命中测试

`effective_island_passthrough()` 里 `drag_active()` 判断在**最前面**，所以守卫一置位就必然可交互，
逻辑本身没问题。问题在**时机**：

- 穿透开着时，岛平时是 `WS_EX_TRANSPARENT`，Windows 的命中测试会**整体跳过**它 → 外来拖拽的
  `DragEnter` 不会投给岛。
- 守卫必须"抢在系统做命中测试之前"把窗口变可交互。而它原来是**120ms** 一轮（后来按开关自适应，
  穿透开着时仍是 120ms）——用户拖动较慢时能看到 `拖拽活跃=true`，但 OLE 的 Enter 已经错过了，
  日志表现就是：**只有 `穿透生效(拖拽活跃=true)`，没有 `[island] 拖入 N 个文件`**。
- 穿透关着时之所以"感觉能用"，是因为光标压在球上时窗口本来就已可交互（按可见内容判定），
  根本不依赖守卫抢跑。**所以问题只在"穿透开"这一侧暴露。**

### 8.4 修复

1. 轮询间隔固定 **30ms**（原来 120ms），并把触发范围从"光标在窗口内"放宽到
   **"窗口外扩 12px"**（`PREARM_MARGIN`）——等于让窗口提前一点进入可交互，降低赛跑失败率。
2. 为了让 30ms 轮询不变成"每秒读盘 30 次"，给岛偏好加了**500ms TTL 缓存**
   （`island_prefs_cached()`；`patch_island_config()` 会主动失效）。
   热路径 `effective_island_passthrough()` 改用缓存版本。

### 8.5 实测（穿透**开着**，即之前失败的那种配置）

```
起始：            穿透生效 = true（用户开关=true 拖拽活跃=false）
按住左键压到岛上：穿透生效 = false（用户开关=true 拖拽活跃=true）   ← 窗口已变可交互，
                                                                   OLE 的 DragEnter 才能投进来
松开（未落岛）：   穿透生效 = true（用户开关=true 拖拽活跃=false）   ← 恢复用户设定
```

> 注：真实的"从资源管理器拖文件"这一步依赖 OLE，无法用合成输入端到端复现，
> 所以这里验证的是**守卫是否按预期把窗口变成可交互**（这正是文件拖放能否送达的前提）。
> 真机拖放仍需人工确认。

### 8.6 人工验收

1. **穿透开着**（Ctrl+Alt+B 切到穿透）→ 从资源管理器拖一个文件到球上 → **应识别并出现转换按钮**。
2. 穿透开着 → 按住球拖：**球不应被拖走**。
3. 穿透关着 → 拖文件到球上照样能识别；按住球可以拖动位置。
4. 拖文件"只是路过"球（没松手在球上）→ 松手后球应恢复穿透，不残留可交互状态。

## 9. 终版方案：消除与系统抢跑（2026-10-16）

### 9.1 为什么前面几轮都没修好

第 8 节的做法是"让守卫抢在系统命中测试之前把窗口变可交互"，但这条路**结构上就不稳**：

> **`WS_EX_TRANSPARENT`（穿透）窗口会被 Windows 鼠标命中测试整体跳过**，
> 连带 **OLE 文件拖放的 DragEnter/Drop 也一并不投递**。

于是"穿透开着还要收文件"只能靠抢跑，而抢跑的探测信号（左键状态 / 鼠标捕获）都不可靠。
这解释了用户观察到的全部现象：

| 状态 | 让窗口变可交互的路径 | 需要抢跑吗 | 结果 |
|---|---|---|---|
| 穿透**关** | `!cursor_over_island_content` —— **只看光标位置** | **不需要** | 一直可用 ✓ |
| 穿透**开** | 只能靠守卫探测"正在拖拽" | 需要 | 抢不赢就完全没反应 ✗ |

### 9.2 终版做法：球身区域两种状态行为一致

- **`effective_island_passthrough()` 不再因"用户开关打开"直接返回 true**；
  判定变成：拖拽/菜单 → 不可穿透；展开态 → 不可穿透；**收起态 → 跟随可见内容（光标在球上就不可穿透）**。
  也就是**球身那块区域在两种状态下完全一样**，文件拖放因此走的正是"穿透关时那条已验证可用的路径"，
  不再依赖抢跑。
- **"穿透"由前端表达成两件事**（这才是用户能感知的差异）：
  1. `.island-shell` 不带 `grabbable` → **不能按住球拖走**（`-webkit-app-region` 是 OS 级行为，只能靠类名开关）；
  2. `.island-shell.passthrough-inert { pointer-events: none }` → **点球不响应**（不会误触球上的按钮/菜单）；
     拖放菜单出现时自动去掉该类，否则格式菜单点不了。

### 9.3 一个必须说清的取舍（平台限制，不是实现偷懒）

Windows 上**同一个像素不可能既"点击穿透到下层"又"接收文件拖放"**——两者走的是同一条命中测试规则。
所以穿透开着时：

- 球**周围那圈透明区**：仍然完全穿透（点击落到桌面）✓
- 球**身上**（可见胶囊那块，约 224×46）：点击会被窗口吞掉但**不做任何事**（`pointer-events:none`），
  不再落到桌面 ✗ —— 这是为了换取"文件能拖上来"。

如果更看重"球身上也必须能点到桌面"，那就只能放弃"穿透时也能接收文件拖放"，二者不可兼得。

### 9.4 实测

```
穿透开 + 光标移到球上  → 穿透生效 = false（用户开关=true …）   ← 与穿透关时一致，文件拖放路径同一套
穿透开 + 光标移开      → 穿透生效 = true （用户开关=true …）   ← 球周围不挡桌面
穿透关 + 光标移到球上  → 穿透生效 = false（用户开关=false …）  ← 对照组
```

> 说明：OLE 拖放的"投递成功"这一步无法用合成输入忠实复现（我用 `DoDragDrop` 写了个助手，
> 发现它并不能模拟资源管理器拖拽的真实命中测试），所以"松手后是否弹出格式菜单"仍需人工确认；
> 但"窗口是否对球身可交互"这一**前提条件**已在两种状态下实测一致。

## 10. 终版（第二稿）：用"按住时长"区分点击与拖放（2026-10-16 晚）

### 10.1 第 9 节方案被用户否掉（它确实错了）

第 9 节为了让"穿透开着也能拖文件"，把球身改成"光标在球上就可交互"，结果**穿透不再是穿透**：
点球不再落到桌面。用户复测后直接指出："开穿透不仅没有出现（识别），还不能穿透了" —— 正确。

### 10.2 实测：系统层面能用的信号只有一个

我写了 `DoDragDrop` 助手发起真实 OLE 拖拽，并在拖拽过程中从外部采样各候选信号：

| 信号 | 拖拽中实测 | 结论 |
|---|---|---|
| `GetCapture()` 鼠标捕获 | **恒为 0** | ✗ 不可用（第 9 节前的方案建立在它之上，是错的） |
| 剪贴板 `CF_HDROP` | **恒为 false** | ✗ 不可用 |
| `GetAsyncKeyState(VK_LBUTTON)` | **true** | ✓ 唯一可用 |

⇒ **系统层面分不出"拖文件"和"按住左键"**。所以"按键+靠近就变可交互"必然会把普通点击也吞掉。

### 10.3 终版做法：按住时长门槛（ARM_DELAY_MS = 220ms）

- 守卫只有在"**左键按住 + 光标在岛附近，且已持续 ≥220ms**"时才临时让窗口退出穿透。
- 依据：**普通点击 50~120ms 就松手**（越不过门槛 → 球保持穿透，点击照常落到下层 ✓）；
  而**把文件拖到球上、停留、再松手**必然超过 220ms（→ 临时可交互 → OLE 才能把文件投给它 ✓）。
- 松手后 500ms 宽限期结束即恢复用户设定的穿透 ✓。
- 同时恢复第 9 节删掉的分支：**用户开关打开 → 恒定穿透**（除拖拽/菜单期间例外）。

### 10.4 实测（穿透**开着**，三档对照）

| 场景 | 期望 | 实测 |
|---|---|---|
| 只悬停（不按键） | 保持穿透（点击落到桌面） | `穿透生效 = true` ✓ |
| **快速点击**（按下 60ms 就松） | 仍穿透（球不响应） | `穿透生效 = true` ✓（未越过 220ms 门槛） |
| **按住 ≥220ms** | 临时退出穿透 → 可接收文件拖放 | `按住 220ms … → 穿透生效 = false（拖拽活跃=true）` ✓ |
| 松手后 | 恢复穿透 | `穿透生效 = true` ✓ |

### 10.5 仍然存在的边界（诚实说明）

- 如果你**故意长按球 220ms 以上**（而不是点击），那一下会被球接收（不落到桌面）——
  这是"能接收文件拖放"必须付出的代价；普通点击不受影响。
- **OLE 的 Drop 在本机始终不投递**（历史日志里 `球上松手` 出现 0 次），实际靠
  "补发 drop"兜底；兜底判定已修（用松手瞬间的光标位置，而不是 500ms 后的位置）。
- 若真机上"按住 ≥220ms 拖文件"仍无反应，下一步就换思路：不再依赖 Enter 记路径，
  改为在拖拽期间通过 `WindowFromPoint` + 剪贴板/`IDataObject` 主动取文件列表。
