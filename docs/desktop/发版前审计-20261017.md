## 1. 🔴 阻塞级：实例守卫会把"安装版自己"当成 Electron 版，导致装完起不来

### 现象
用 NSIS 安装包安装后双击启动**毫无反应**（无窗口、无托盘、连日志都不写）。

### 根因
`lib.rs::conflicting_instance_running()` 扫 `tasklist`，**只要发现名为 `shortcut.exe` 的进程就报冲突**
并弹框 `exit(1)`。而：

- 打包出来的安装版进程名正是 **`ShortCut.exe`**（`productName = "ShortCut"`）；
- 原实现**既不排除自身 PID，也不比对路径**。

⇒ 程序把自己认成"旧版 Electron 版在运行"，自己把自己拦在启动之前。
（本地做 `install-local.ps1` 时把安装文件命名成 `ShortCut.exe`，已提前复现同一现象。）

### 修复
两条判据都满足才算冲突：
1. 该 PID ≠ `std::process::id()`（排除自己）；
2. 该进程的可执行文件路径 ≠ 自己所在的路径（同名但**不同副本**才当旧版；同路径多开交给
   `tauri-plugin-single-instance` 的命名互斥体处理）。

### 验证（决定性）
把新构建的 exe 命名成 `ShortCut.exe`、连同 `app_lib.dll` 放到临时目录直接启动：

```
✓ 启动成功  pid=3132  路径=…\sc-install-test\ShortCut.exe
```

修复前该场景会静默退出。**这条验证必须在每次改守卫逻辑后重跑。**

## 2. 🔴 阻塞级：侧车与静态页用"编译期绝对路径"，换台机器就全失效

### 现象（在非开发机上）
驾驶舱温度（硬件监控）、音乐桥、语音胶囊、局域网控制页会**失效**——因为程序去找
`D:\wenjian\js\ShortCut\src-tauri\..\resources\...`（构建机的路径）。

### 根因
以下位置直接把 `env!("CARGO_MANIFEST_DIR")` 当运行时路径：

| 位置 | 目标 |
|---|---|
| `sidecar.rs`（hardware_monitor_exe） | `resources/hardware-monitor/ShortCut.HardwareMonitor.exe` |
| `sidecar.rs`（music_bridge_script） | `resources/music-bridge/netmusic-bridge.ps1` |
| `voice.rs`（bridge_script_path） | `resources/scripts/voice-input-bridge.ps1` |
| `lib.rs`（`sj_static_root_pub`） | `resources/sj`（局域网控制静态页、音乐岛页） |

而且 `tauri.conf.json` 的 `bundle.resources` **只打包了 `sj/*` 与 `scripts/*`**：
`hardware-monitor`、`music-bridge`、`usage-monitor` 根本没进安装包。

### 修复
1. 新增统一解析（`lib.rs`）：
   - `resources_root()`：先试 **`<exe 所在目录>/resources`**（Tauri bundler 的安装布局），
     再回退 `CARGO_MANIFEST_DIR/../resources`（开发时从 `target/` 直接跑）；
   - `resource_path(rel)`：取 `resources/` 下具体文件。
2. 上述 4 处改为 `resource_path(...)` 优先、原开发路径保留为第二候选（不破坏开发流程）。
3. `bundle.resources` 补上 `hardware-monitor/*`、`music-bridge/*`、`usage-monitor/*`。

> 注：`cloud.rs` / `control.rs` 里各有一处同样的写法，但都在 `#[cfg(test)]` 内，不影响运行时（未改）。

## 4. 发布流程（照此执行）

> 🔴 **`npx tauri build` 必须在 `vcvars64` 环境里跑**（本次踩到）：
> 直接在当前 shell 里跑会以如下错误失败——
> ```
> corecrt.h(10): fatal error C1083: 无法打开包括文件: "vcruntime.h": No such file or directory
> error occurred in cc-rs: … cl.exe … lzma-sys-0.1.20 … x86.c
> ```
> 原因：打包链路里的 `lzma-sys`（压缩用）需要 **C 编译器**，而 `cl.exe` 依赖 VS 环境变量
> （`INCLUDE`/`LIB`/`PATH`）。`cargo build` 我们一直是用 `vcvars64.bat && cargo build` 包的，
> 所以没暴露；`tauri build` 直接调用就缺了这层环境。
> **修法**：把 `tauri build` 也放进 `call vcvars64.bat && …` 里跑（见下面命令）。

```powershell
# 0) 版本号三处同步（Cargo.toml / tauri.conf.json / package.json）
# 1) 前端必须先构建（frontendDist 是编译期嵌入的，顺序反了会得到"健康但界面是上一版"的 exe）
npm run build

# 2) 打包 + 签名：**必须在 vcvars64 环境里**
$env:TAURI_SIGNING_PRIVATE_KEY_PATH = "$env:USERPROFILE\.tauri\shortcut-updater.key"
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = ''
cmd /c 'call "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvars64.bat" >nul 2>&1 && npx tauri build --features custom-protocol'

# 产物：
#   src-tauri/target/release/bundle/nsis/ShortCut_<ver>_x64-setup.exe
#   src-tauri/target/release/bundle/nsis/ShortCut_<ver>_x64-setup.exe.sig

# 3) 上传到服务器 /www/wwwroot/ShortCut/updates/（安装包 + .sig）
# 4) 更新 /updates/latest.json（version / pub_date / url / signature=**.sig 文件全文**）
#    细节见 docs/server/updater-deploy.md
```

⚠️ **第 4 步会让已安装用户下次启动时收到更新**（2.4.6 → 新版）。所以：
**先本地装一次安装包确认能用，再改线上 latest.json。**

## 5. 遗留风险（不阻塞本次发布，但要知道）

| 风险 | 说明 | 建议 |
|---|---|---|
| NSIS 安装包**未做代码签名** | Windows SmartScreen 会提示"未知发布者" | 有证书后补签 |
| 自启指向安装目录的固定路径 | 用户移动安装目录会失效 | 正常安装版不受影响（安装向导决定路径） |
| 旧配置兼容 | 用户已有 `%APPDATA%\ShortCut\shortcut\config.json`；本次没改结构 | 若以后改配置结构，记得写迁移（参考 `migrate_ball_shortcut_default`） |
| 拖放依赖"普通权限启动" | 以管理员运行会让外部拖放整体失效（UIPI） | 应用已内置提权告警日志；安装包默认普通权限启动 ✓ |
| 穿透开着时文件拖放仍不可用 | 平台限制（`WS_EX_TRANSPARENT` 窗口被命中测试整体跳过），详见 `球穿透开关修复说明.md` §10 | 已与用户达成一致：保持现状 |
